Part I - Product Requirements Document
1. Product Overview
The proposed platform creates a cooperative-owned digital marketplace connecting verified labour
cooperative workers with households, businesses and institutions that require services. The source
problem statement identifies service-provider registration and verification, skill profiling, booking,
geo-based matching, payments, ratings, welfare/insurance, emergency booking, federation
administration, multilingual support and AI-based demand forecasting/workforce allocation as
expected solution areas.
Product objective
• Digitize cooperative worker availability and skills.
• Make service discovery and booking simple for customers.
• Increase trust through verification, certification and ratings.
• Support transparent booking, payment and invoicing.
• Help cooperatives monitor operations and allocate workforce using analytics and AI.

9. System Architecture
The proposed MVP uses a client-server architecture with a shared backend API, relational data store,
geo-spatial search and a separate AI service. This keeps the marketplace usable independently from
forecasting while allowing AI to consume historical booking data.

13. Worker Matching Engine

--- PAGE BREAK ---
Cooperative Gig Services Platform - SIH PS 26089
Page 9
The matching engine should first reduce the candidate pool and then rank the remaining verified
workers. A practical prototype score is: 35% skill match, 25% distance, 20% availability, 10% rating
and 10% reliability. These weights are proposed and should be tuned with real booking data.
Request
↓
Filter by required skill
↓
Filter verified workers
↓
Filter availability
↓
Search within radius using PostGIS
↓
Calculate matching score
↓
Rank workers
↓
Notify highest-ranked candidates
Emergency requests should increase the weight of proximity, availability and response time.
14. AI Demand Forecasting
The AI service is designed as an independent module that consumes historical booking data and
returns forecasts by service, location and time period. The prototype should start with interpretable
tabular/time-series approaches and be evaluated using validation data before selecting the final
model.

• Hash passwords using a strong password hashing algorithm.

CUSTOMER APP ─┐
WORKER APP ─┼─→ BACKEND API ─→ POSTGRESQL/POSTGIS

├─→ REDIS
├─→ PAYMENTS
├─→ NOTIFICATIONS
└─→ AI SERVICE
│
├─ Demand Forecasting

The core design principle is to make the marketplace fully functional without AI, then use accumulated
booking data to strengthen forecasting and workforce planning. This reduces demo risk while
preserving the advanced capability required by the problem statement.
